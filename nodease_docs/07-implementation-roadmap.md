# 구현 로드맵

## 목표

다음 주 데모에서는 모든 기능을 완성하기보다, Nodease가 "기업용 AI Workflow / LLMOps 플랫폼"이라는 방향을 납득시킬 수 있는 핵심 장면을 만들어야 한다.

## P0: 먼저 보여줄 것

### 1. LLMOps Gateway 관측성

- 워크플로우 실행 시 노드별 모델, 토큰, 비용, 지연시간 저장
- 실행 상세 화면에서 노드별 비용/시간 표시
- 모델별/워크플로우별 사용량 요약

완료 기준:

- 하나의 워크플로우 실행 결과에서 어느 노드가 어떤 모델을 얼마의 비용으로 호출했는지 볼 수 있다.

### 2. 모델/프롬프트 비교와 추천

- 동일 입력으로 모델 A/B 실행
- 프롬프트 버전별 결과 비교
- 비용, latency, 간단한 품질 지표 표시
- 품질 점수가 아직 정교하지 않다면 사용자 평가 또는 rule-based check로 시작

완료 기준:

- "이 모델이 더 싸고 품질 차이가 작아 보인다"는 근거 기반 제안이 UI에 나온다.

### 3. 감사 로그

- 워크플로우 실행 로그
- 프롬프트/모델/워크플로우 변경 로그
- 사용자, 시각, action, target 저장

완료 기준:

- 관리자가 "누가 언제 무엇을 실행/수정했는지" 조회할 수 있다.

### 4. RBAC 최소 구현

- 프로젝트/캔버스 read/write/execute
- 데이터 소스 read/use 권한
- 모델 사용 권한 제한

완료 기준:

- 권한 없는 사용자가 특정 데이터 소스나 모델을 쓰려 하면 차단된다.

### 5. RAG 데이터 갱신/청크 감사

- 데이터 소스 변경 감지 상태 표시
- full re-index / partial re-index / incremental indexing 옵션 설명
- 어떤 문서/청크가 검색되고 LLM에 전달됐는지 추적
- 변경된 문서만 재처리하는 데모 흐름, 가능하면

완료 기준:

- 데이터가 고정되지 않는 상황과 "어떤 청킹이 어디서 쓰였는지"를 제품이 고려하고 있음을 보여준다.

### 6. 에디터 UX와 설정 편의성

- 복잡한 property settings를 더 빠르게 이해할 수 있게 정리
- 추천/비교 액션을 캔버스 옆 패널에서 바로 실행
- 노드 실행 결과의 비용/시간/오류를 캔버스에서 확인

완료 기준:

- Moduly보다 설정을 찾고 바꾸기 쉽다는 인상을 준다.

## 이번 주 리서치 질문

1. LLMOps Gateway 제품들은 공통적으로 어떤 기능을 제공하는가?
2. LLMOps를 도입하면 기업에서 어떤 새로운 운영 문제가 생기는가?
3. RAG 데이터가 계속 바뀔 때 industry standard는 무엇인가?
4. 품질 점수는 어떤 방식으로 정의하고 측정할 수 있는가?
5. 로그가 매우 많아질 때 저장, 검색, 보존 정책은 어떻게 잡는가?
6. RBAC를 데이터 소스/프로젝트/모델 어디까지 적용하는 것이 현실적인가?

## 데모 시나리오

```text
1. Builder가 고객 문의 처리 워크플로우를 만든다.
2. RAG 데이터 소스를 연결한다.
3. Workflow를 테스트 실행한다.
4. 실행 결과 화면에서 노드별 비용, latency, 모델, token을 본다.
5. 추천 패널이 "이 노드는 더 싼 모델로 대체 가능"하다고 제안한다.
6. Prompt A/B 테스트를 실행해 품질과 비용을 비교한다.
7. Admin이 HR 데이터 소스 권한을 제한한다.
8. 권한 없는 사용자의 실행이 차단된다.
9. Audit Log에서 실행, 차단, 변경 이력을 확인한다.
10. 데이터가 변경된 문서만 partial re-index한다.
```

## 구현 범위 조절 원칙

- 먼저 실제 실행 로그와 비용 표시를 만든다.
- 다음으로 추천/비교 UI를 붙인다.
- 정책 엔진은 완전한 범용 규칙 엔진보다 명확한 몇 개의 정책부터 구현한다.
- 컴플라이언스는 "인증 완료"가 아니라 "준비 가능한 구조"로 표현한다.
- 노드 단위 권한은 후순위로 두고, 프로젝트/데이터 소스/모델 권한부터 만든다.
