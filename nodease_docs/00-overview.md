# Nodease Overview

작성 기준: [memo.md](./memo.md)와 `local/nodease_docs`의 정리 문서 전체

## Executive Summary

Nodease는 단순한 노드 기반 자동화 도구가 아니라, 기업이 AI 워크플로우를 안전하게 설계, 실행, 비교, 배포, 감사, 최적화할 수 있는 AI Workflow / LLMOps 운영 플랫폼으로 포지셔닝해야 한다.

핵심은 "예쁜 캔버스"가 아니라 운영 가능성이다. 기업 입장에서는 워크플로우가 실행되는 것만으로 부족하다. 누가 어떤 모델을 썼는지, 어떤 데이터가 모델로 전달됐는지, 비용은 어디서 발생했는지, 실패는 어느 노드에서 났는지, 권한 없는 사용자가 민감 데이터에 접근하지 않았는지, 배포 후에도 로그와 정책을 추적할 수 있는지가 중요하다.

따라서 Nodease의 중심 메시지는 다음과 같다.

```text
기업용 AI Workflow / LLMOps 운영 플랫폼
  = Workflow Builder
  + LLM Gateway
  + Cost / Quality Optimization
  + RAG / Data Governance
  + Audit / Tracing
  + RBAC
  + Enterprise UX
```

## 해석 기준

`memo.md`에는 원문 메모와 ChatGPT 요약이 함께 있다. 정리 문서에서는 둘을 구분한다.

| 구분 | 처리 방식 |
| --- | --- |
| 원문에서 반복된 요구 | 제품 중심축으로 반영 |
| 원문에서 파생 가능한 기능 | 기능 후보로 정리 |
| ChatGPT 요약에서 확장된 해석 | 보조 메시지 또는 리서치 후보로 취급 |

가장 중요한 보정은 "멀티에이전트 플랫폼"을 중심 메시지로 고정하지 않는 것이다. 멀티에이전트는 보조 설명으로 쓸 수 있지만, 원문 직접 요구는 LLMOps Gateway, audit, RBAC, RAG 데이터 갱신, 비용 최적화, tracing, data governance, editor UX에 더 가깝다.

## 제품 정의

Nodease는 사용자가 AI 워크플로우를 노드 기반으로 설계하고, 실행 전에 모델/프롬프트/데이터 정책을 검증하며, 배포 후에는 비용, 실패, 데이터 흐름, 권한 위반, 실행 이력을 추적할 수 있게 하는 기업용 AI 운영 플랫폼이다.

### 기존 도구처럼 보이면 약한 지점

- n8n 스타일의 노드 연결 도구
- 단순 프롬프트 실행 데모
- 드래그 앤 드롭 워크플로우 빌더
- 실행 결과만 보여주는 자동화 도구

### Nodease가 강조해야 할 지점

- LLMOps Gateway가 내장된 워크플로우 빌더
- 노드별 비용, 토큰, 지연시간, 실패 추적
- 모델/프롬프트/청크 전략 비교와 추천
- RAG 데이터 변경과 재색인 전략 관리
- 데이터 리니지와 PII/Confidential 데이터 통제
- 실행/수정/배포/권한 변경에 대한 감사 로그
- 프로젝트/캔버스/데이터 소스 단위 RBAC
- Moduly보다 편한 property settings와 비교 중심 UX

## 핵심 제품 축

### 1. LLMOps Gateway

LLMOps Gateway는 Nodease의 중심 기능이다. 단순히 모델 API를 호출하는 계층이 아니라, 모델 사용을 통제하고 운영 데이터를 남기는 계층이어야 한다.

필수 기능:

- 사용자/역할/프로젝트별 모델 사용 제한
- 워크플로우/노드/모델/프롬프트 단위 tracing
- 노드별 비용, 토큰, 지연시간, 실패 기록
- 모델별/프로젝트별/사용자별 사용량 집계
- 정책 위반 요청 차단 또는 경고

확장 후보:

- cache 기반 cost saving
- fallback/retry
- rate limit
- 모델 라우팅
- MCP Gateway와의 연동

초기 데모에서는 fallback이나 rate limit보다 "누가 어떤 노드에서 어떤 모델을 얼마의 비용으로 호출했는지"를 명확히 보여주는 것이 우선이다.

### 2. Cost / Quality Optimization

메모는 싼 모델 추천, A/B 테스트, quality score, 프롬프트 suggestion, 청크 최적화를 반복해서 언급한다. 즉 Nodease는 trial-and-error를 체계화해야 한다.

비교 대상:

- 모델: 비용, 지연시간, 품질, 실패율
- 프롬프트: 토큰 수, 응답 품질, 정책 위반 여부
- 청크 설정: chunk size, overlap, top-k, 검색 품질, 비용
- 워크플로우: 병목 노드, 전체 비용, 실패 지점

주의할 점:

- "비싼 모델 = 항상 좋은 품질"이라고 가정하면 안 된다.
- quality score는 아직 모호하므로 단일 지표로 과장하지 않는다.
- 초기에는 사용자 평가, rule-based check, 샘플 입력 결과 비교처럼 단순한 방식으로 시작한다.

### 3. RAG / Data Governance

원문은 "요즘 프롬프트 엔지니어링보다 청크 엔지니어링이 중요하다"고 본다. 특히 데이터가 고정되어 있지 않고 계속 들어오는 현실을 반영해야 한다.

핵심 질문:

- 데이터가 바뀌면 전체를 다시 색인해야 하는가?
- 바뀐 문서나 청크만 부분 갱신할 수 있는가?
- incremental indexing이나 CDC가 필요한가?
- PII가 포함된 데이터는 어떻게 탐지하고 처리할 것인가?
- 어떤 청크가 검색되어 어떤 모델에 들어갔는지 추적할 수 있는가?

초기 방향:

- full re-index / partial re-index / incremental indexing 옵션을 보여준다.
- 데이터 소스 변경 상태를 표시한다.
- 어떤 문서/청크가 검색되고 LLM에 전달됐는지 감사 가능하게 만든다.
- "완전 자동 최적 RAG"보다 "RAG/청크 audit"을 먼저 구현한다.

### 4. Audit / Tracing

기업용 제품에서 audit은 핵심이다. 원문은 AWS처럼 한 건 한 건 기록되는 audit 관점을 강조한다.

남겨야 할 로그:

- 누가 실행했는지
- 언제 실행했는지
- 어떤 워크플로우/노드가 실행됐는지
- 어떤 모델과 프롬프트가 사용됐는지
- 어떤 데이터/청크가 모델에 전달됐는지
- 비용, 토큰, 지연시간은 얼마였는지
- 실패는 어디서 발생했는지
- 누가 워크플로우, 모델, 프롬프트, 정책, 권한을 수정했는지
- 누가 배포, 롤백, 실행을 수행했는지

초기에는 로그를 많이 남기는 것 자체보다, 검색 가능한 형태로 남기는 것이 중요하다. 기간, 사용자, 워크플로우, 노드, 모델, 데이터 등급, 성공/실패, 정책 위반 여부로 필터링할 수 있어야 한다.

### 5. RBAC

원문은 RBAC를 직접 요구한다. 다만 노드 단위 권한은 복잡도가 높으므로 우선순위를 낮춘다.

초기 권한 범위:

- 프로젝트: read / write / admin
- 캔버스: read / write / execute
- 데이터 소스: read / use / manage
- 모델: use / manage

우선 데모에서는 "HR 데이터 소스는 HR 그룹만 사용 가능" 같은 시나리오가 가장 명확하다. 권한 없는 사용자가 해당 데이터 소스를 포함한 워크플로우를 실행하면 차단되고, 그 차단 이력이 audit log에 남아야 한다.

### 6. Enterprise UX

원문은 Moduly의 에디터와 property settings가 충분히 편하지 않다는 점을 언급한다. 따라서 기능을 많이 넣는 것만큼, 설정과 비교를 쉽게 만드는 UX가 중요하다.

필요한 UX:

- 노드 설정을 빠르게 이해하고 수정할 수 있는 property panel
- 모델/프롬프트/청크 추천 버튼
- A/B 테스트 결과 비교 패널
- 노드별 비용/시간/오류를 캔버스에서 바로 확인
- 정책 위반 또는 권한 차단 상태를 명확히 표시
- 실행 로그와 추적 정보를 노드에서 자연스럽게 연결

## Runtime 고려사항

Nodease는 DAG 그래프를 실행하는 도구이므로 실행 모델도 고민해야 한다.

고려할 항목:

- 스케줄 실행
- 비동기 노드 실행
- 응답 속도가 다른 노드 결과를 merge하는 방식
- 실패한 노드 재시도 또는 중단 정책
- 실행 결과와 audit log의 연결

이 영역은 P0보다 P1에 가깝지만, 설계상 빠뜨리면 나중에 구조 변경 비용이 커질 수 있다.

## 데모 우선순위

P0는 다음 주 데모에서 제품 방향을 설득하기 위해 필요한 최소 범위다.

| 우선순위 | 기능 | 완료 기준 |
| --- | --- | --- |
| P0 | LLMOps Gateway 관측성 | 노드별 모델, 비용, 토큰, 지연시간, 실패를 볼 수 있다 |
| P0 | 모델/프롬프트 비교 | 동일 입력에 대해 모델/프롬프트 결과와 비용을 비교한다 |
| P0 | Audit Log | 누가 언제 무엇을 실행/수정했는지 조회할 수 있다 |
| P0 | RBAC 최소 구현 | 권한 없는 데이터 소스/모델 사용이 차단된다 |
| P0 | RAG 데이터 갱신/청크 감사 | 데이터 변경과 사용된 청크를 추적할 수 있다 |
| P0 | Editor UX | 설정, 추천, 비교가 기존보다 찾기 쉽다 |
| P1 | Cache / fallback / retry | 운영 안정성과 비용 절감을 강화한다 |
| P1 | 데이터 리니지 뷰 | 데이터 흐름을 시각적으로 추적한다 |
| P1 | 로그 검색/aggregation | audit log를 운영 관점에서 분석한다 |
| P1 | DAG 스케줄링/merge 정책 | 실행 모델을 더 현실적으로 만든다 |
| P2 | Kubernetes / SaaS / Open Source 전략 | 배포 형태를 결정한다 |
| P2 | 노드 단위 권한 | 세밀 권한을 확장한다 |
| P2 | 컴플라이언스 리포트 | 규제 대응 문서화를 자동화한다 |

## 권장 데모 시나리오

```text
1. Builder가 고객 문의 처리 워크플로우를 만든다.
2. RAG 데이터 소스를 연결한다.
3. 워크플로우를 테스트 실행한다.
4. 캔버스에서 노드별 모델, 비용, 토큰, 지연시간, 실패 여부를 확인한다.
5. 추천 패널이 더 싼 모델 또는 더 짧은 프롬프트를 제안한다.
6. 모델/프롬프트 A/B 테스트로 비용과 품질을 비교한다.
7. Admin이 HR 데이터 소스 권한을 HR 그룹으로 제한한다.
8. 권한 없는 사용자가 실행하면 차단된다.
9. Audit Log에서 실행, 차단, 변경 이력을 확인한다.
10. RAG 데이터가 변경되면 변경 문서만 partial re-index하고, 사용된 청크를 추적한다.
```

이 시나리오는 원문의 핵심 요구인 LLMOps, cost optimization, RAG 데이터 갱신, audit, RBAC, editor UX를 한 번에 보여준다.

## 말하면 안 되는 것 / 조심할 표현

아래 표현은 과장으로 보일 수 있으므로 조심한다.

- "GDPR/HIPAA/ISMS를 준수한다"
- "완전 자동으로 최적 RAG를 만든다"
- "멀티에이전트가 제품의 핵심이다"
- "비싼 모델이 항상 품질이 좋다"
- "노드 단위 권한까지 모두 지원한다"

대신 이렇게 표현하는 것이 안전하다.

- "규제 대응을 준비할 수 있는 audit/data governance 구조를 제공한다"
- "청크/검색/색인 과정을 추적하고 비교할 수 있다"
- "기업용 LLMOps 운영 문제를 캔버스 경험 안에 통합한다"
- "비용, 지연시간, 품질 지표를 근거로 모델/프롬프트 선택을 돕는다"
- "초기 권한 모델은 프로젝트/캔버스/데이터 소스 중심이다"

## 아직 확인해야 할 모호한 지점

| 항목 | 확인 필요 |
| --- | --- |
| MCP Gateway | LLMOps Gateway 내부 기능으로 둘지, 별도 계층으로 둘지 |
| Quality Score | 어떤 평가 지표를 P0에서 사용할지 |
| Cost Management | 배포 후 비용 제어인지, 가격 정책인지, 추천 기능인지 |
| RAG 자동화 범위 | 자동 최적화까지 할지, audit/비교까지만 할지 |
| 배포 형태 | SaaS, Open Source, Kubernetes 중 무엇을 우선할지 |
| End-to-End 범위 | 다음 주 데모에서 실제 구현과 스펙 문서의 경계 |

## 최종 방향

Nodease는 "워크플로우를 그리는 도구"보다 "기업이 AI 워크플로우를 실제로 운영할 수 있게 만드는 도구"로 보여야 한다. 따라서 다음 개발 우선순위는 기능 수를 늘리는 것이 아니라, 기존 워크플로우 실행 경험 위에 LLMOps 관측성, 비용/품질 비교, RAG/청크 감사, RBAC, audit log, 편한 설정 UX를 얹는 것이다.
