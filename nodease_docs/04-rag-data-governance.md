# RAG, 동적 데이터, 데이터 거버넌스

## 메모의 문제의식

메모는 "요즘 프롬프트 엔지니어링보다 청크 엔지니어링과 RAG 운영 문제가 중요하다"고 말한다. 특히 데이터가 고정되어 있지 않고 계속 바뀌는 경우를 고려해야 한다.

핵심 질문은 다음과 같다.

- RAG 데이터가 자주 바뀌면 전체를 다시 색인해야 하는가?
- 바뀐 문서나 청크만 부분 갱신할 수 있는가?
- 데이터 수집 과정에서 누락, 중복, 삭제를 어떻게 처리하는가?
- PII가 포함된 문서를 어떻게 탐지하고 마스킹할 것인가?
- 어떤 데이터가 어떤 모델에 전달됐는지 어떻게 추적할 것인가?

## 동적 데이터 갱신 전략

| 전략 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| Full Re-index | 전체 데이터를 다시 파싱/청킹/임베딩 | 단순하고 일관성 높음 | 비용과 시간이 큼 |
| Partial Re-index | 변경된 문서만 다시 처리 | 비용 절감 | 변경 감지 필요 |
| Incremental Indexing | 변경된 청크 단위로 추가/수정/삭제 | 대규모 운영에 적합 | 구현 복잡도 높음 |
| CDC 기반 Sync | DB 변경 로그를 읽어 갱신 | 실시간성 높음 | 데이터 소스별 구현 필요 |
| Scheduled Sync | 주기적으로 변경 여부 확인 | 구현 쉬움 | 실시간성 낮음 |
| Webhook Sync | 외부 시스템 이벤트로 갱신 | 효율적 | 연동 시스템 의존 |

## 청킹 최적화 관점

청크는 비용과 품질에 직접 영향을 준다.

- chunk size가 크면 문맥은 풍부하지만 토큰 비용이 증가한다.
- chunk size가 작으면 비용은 낮지만 문맥 부족으로 답변 품질이 낮아질 수 있다.
- overlap이 크면 검색 안정성은 올라가지만 중복 토큰 비용이 증가한다.
- top-k가 크면 recall은 올라가지만 비용과 지연시간이 증가한다.

따라서 Nodease는 청킹 설정을 단순 옵션이 아니라 비교/추천 대상으로 다뤄야 한다. 다만 원문에는 "최적 RAG 시스템을 완전히 자동으로 만들기보다는 audit이 중요하다"는 방향도 있으므로, 초기 구현은 자동 최적화보다 청크/검색/색인 이력을 보여주는 쪽이 더 안전하다.

## 추천 기능 예시

```text
Chunk Optimization Suggestions
  - 현재 chunk size는 평균 토큰 수가 높아 비용이 큼
  - overlap을 200에서 80으로 줄이면 검색 품질 손실 없이 비용 감소 예상
  - top-k 8과 top-k 4의 품질 차이가 작으므로 top-k 4 추천
  - 최근 문서 변경량이 작으므로 full re-index 대신 partial re-index 추천
```

초기 데모에서는 위 추천을 완전 자동 의사결정으로 만들기보다, "현재 설정이 어떤 비용/품질/색인 영향을 만드는지 보여주고 사용자가 선택하게 하는 형태"가 적절하다.

## 데이터 분류

기업용 제품에서는 데이터 등급이 필요하다.

| 등급 | 의미 | 처리 정책 예시 |
| --- | --- | --- |
| Public | 공개 가능 데이터 | 일반 모델 호출 가능 |
| Internal | 내부 업무 데이터 | 조직 내부 사용자만 접근 |
| Confidential | 민감한 회사 데이터 | 외부 전송 제한, 승인 필요 |
| PII | 개인정보 | 마스킹 또는 외부 모델 차단 |
| PHI | 의료정보 | HIPAA 대응이 필요할 때 확장 검토 |
| Financial | 재무/결제 데이터 | 강한 감사 로그와 권한 필요 |

## 데이터 리니지

데이터 리니지는 "데이터가 어디서 와서 어디로 갔는지"를 보여주는 기능이다.

```text
Customer DB
  -> Document Loader
  -> PII Detection
  -> Chunking
  -> Embedding
  -> Vector Store
  -> Retrieval Node
  -> LLM Gateway
  -> Slack / CRM / Report
```

각 단계에서 다음 정보를 추적하면 좋다.

- 데이터 소스
- 문서 버전
- 청크 ID
- 임베딩 모델
- 검색된 chunk list
- LLM에 전달된 context
- 데이터 등급
- PII 탐지 여부
- 정책 통과/경고/차단 상태
- 최종 출력 위치

## 글로벌 정책과 노드별 정책

거버넌스는 노드별 설정만으로 부족하다. 기업은 조직 전체 정책을 중앙에서 관리하고, 필요할 때 워크플로우나 노드 단위로 override해야 한다.

```text
Global Governance Policy
  - 데이터 등급별 외부 모델 호출 가능 여부
  - PII 마스킹 정책
  - 데이터 소스별 접근 권한
  - 감사 로그 보존 기간
  - 비용 한도

Workflow / Node Override
  - 특정 노드는 human approval 필수
  - 특정 노드는 더 강한 마스킹 적용
  - 특정 노드는 사내 모델만 사용
  - 특정 노드는 외부 API 호출 금지
```
