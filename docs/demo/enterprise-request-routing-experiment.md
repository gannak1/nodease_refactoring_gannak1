# 엔터프라이즈 통합 업무 요청 모델 라우팅 실험

Status: Draft

## 실험 목적

`엔터프라이즈 통합 업무 요청 처리` 배포에 서로 다른 업무 문의 50건을 보내 다음을 확인한다.

- 매 요청이 네 개의 고정 입력군 중 적절한 입력군으로 판정되는가
- 입력군별 검증 결과에 따라 실제 선택 모델이 달라지는가
- 10회마다 정책 점검이 실행되고 정책·검증 상태가 안정적으로 저장되는가
- 보안·개인정보 사고가 저위험 입력군으로 잘못 분류되지 않는가
- 실행 중에는 Judge LLM을 호출하지 않고 저장된 정책만 평가하는가
- RAG 검색과 JSON 출력 계약을 유지한 채 workflow가 끝까지 성공하는가

이 실험의 초점은 **새 입력군 자동 발견**이 아니다. 이미 정의한 네 입력군의 분류와 모델 선택을 검증한다. 예상하지 않은 자동 입력군이 생기면 성공으로 보지 않고 오탐 가능성으로 기록한다.

## 대상

| 항목 | 값 |
| --- | --- |
| Workflow | `10200000-0000-0000-0000-000000000510` |
| Deployment | `10200000-0000-0000-0000-000000000610` |
| LLM node | `llm-request` |
| 기본 모델 | `gpt-5.6-luna` |
| 제외 모델 | `gpt-5.6-sol` |
| 정책 점검 주기 | 배포 후 성공 실행 10회 |
| 월간 검증 한도 | `$3` |

## 입력군과 데이터셋

| 입력군 | 건수 | 다루는 문의 | 예시 |
| --- | ---: | --- | --- |
| `routine_usage_guidance` | 12 | 메뉴 위치, 화면 설정, 다운로드, 템플릿 등 저위험 사용 안내 | 보관한 workflow를 다시 여는 경로 |
| `account_access_request` | 12 | SSO, MFA, VPN, Git, 임시 관리자와 권한 회수 | 퇴사한 외주 인력의 VPN/Git 권한 회수 |
| `finance_closing_approval` | 13 | 결산, 지급, 증빙, 예산과 역할 분리 | 해외 공급사 지급의 누락 증빙 확인 |
| `security_privacy_incident` | 13 | 개인정보 노출, 계정 탈취, 키 유출, 악성코드와 침해 대응 | 외부 메일로 전송된 고객 명단 대응 |

50개 요청은 공통 문장 틀에 값만 바꾼 데이터가 아니다. 각 요청은 부서, 요청자 역할, 문장 구조와 업무 상황을 별도로 작성했다.

## 실행 순서

순서는 seed `270`으로 재현 가능하게 섞는다. 정책 점검 직전의 입력 분포가 한 입력군에 치우치지 않도록 각 10건 구간에는 네 입력군이 최소 2건씩 포함된다.

| 구간 | 단순 안내 | 계정·권한 | 재무 | 보안 |
| --- | ---: | ---: | ---: | ---: |
| 1~10 | 3 | 3 | 2 | 2 |
| 11~20 | 2 | 2 | 3 | 3 |
| 21~30 | 3 | 2 | 3 | 2 |
| 31~40 | 2 | 3 | 2 | 3 |
| 41~50 | 2 | 2 | 3 | 3 |

10, 20, 30, 40, 50회 직후에는 비동기 정책 갱신과 Replay 검증이 끝날 때까지 기다린 뒤 정책 상태를 기록한다.

## 기대 RAG 동작

- 단순 안내: 사내 온보딩·사용 안내 문서
- 계정·권한: 접근 권한 및 개발 온보딩 규칙
- 재무: 재무 온보딩, 예산 경보와 지급 승인 문서
- 보안: 개인정보·보안 사고 대응 문서

RAG 품질은 출처 문서명만으로 단정하지 않는다. 실행별 검색 문서 수, 검색 chunk 수, JSON schema 상태와 workflow 최종 상태를 함께 확인한다.

## 합격 기준

| 기준 | 합격값 |
| --- | --- |
| 배포 실행 | 50/50 성공 |
| 입력군 판정 | 기대 입력군과 90% 이상 일치 |
| 보안 입력군 | 다른 입력군으로 오분류 0건 |
| 정책 점검 | 10·20·30·40·50회 모두 완료 |
| runtime Judge | 0회 |
| 모델 다양성 | 검증 후 실제 선택 모델 2개 이상 |
| 검증 비용 | 월간 `$3` 이하 |
| 자동 입력군 | 예상 밖 입력군 없음 |

50건이 모두 성공해도 한 모델만 계속 사용했다면 라우팅 검증은 실패로 판정한다.

## 재현 방법

PowerShell에서 데모 비밀번호를 현재 프로세스 환경변수에만 넣고 실행한다.

```powershell
$env:NODEASE_DEMO_PASSWORD = '데모 계정 비밀번호'

python .\scripts\experiment_enterprise_request_routing.py `
  --mode preflight `
  --base-url http://localhost

python .\scripts\experiment_enterprise_request_routing.py `
  --mode execute `
  --base-url http://localhost `
  --confirm-live

Remove-Item Env:\NODEASE_DEMO_PASSWORD
```

원격 서버에서는 `--base-url`만 서버 주소로 바꾼다. 스크립트는 DB에 직접 연결하지 않으므로 같은 API 계약으로 재현할 수 있다.

## 결과물

실행 결과는 `reports/model-routing/enterprise-request-routing/<run-name>/` 아래에 저장한다.

- `state.json`: 중단 후 `--resume`할 수 있는 체크포인트
- `result.json`: 실행별 safe summary와 정책 snapshot
- `report.md`: 사람이 읽는 최종 분석 보고서

비밀번호, API key, credential 원문, 실제 고객 데이터와 LLM 원문 출력은 저장하지 않는다.
