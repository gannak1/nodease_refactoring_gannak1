# 엔터프라이즈 통합 업무 요청 모델 라우팅 50회 실험 결과

Status: Draft

## 결론

2026년 7월 15일 로컬 배포 API를 대상으로 서로 다른 업무 문의 50건을 실제 실행했다.

- Workflow 실행: 50/50 성공
- LLM 노드 실행: 50/50 성공
- JSON 출력 계약: 50/50 통과
- 운영 관찰 저장: 50건
- 기존 입력군에 연결된 관찰: 2건
- 후보 모델 Replay 검증 batch: 0건
- 실제 사용 모델: `gpt-5.6-luna` 50건
- runtime Judge 호출: 0건

실행·RAG·로그 수집·10회 단위 정책 점검은 동작했다. 그러나 입력군 판정에 필요한 증거가 쌓이지 않아 후보 모델 검증과 입력군별 모델 선택은 시작되지 않았다. 따라서 이번 실험의 **워크플로우 실행 검증은 통과**, **적응형 모델 라우팅 검증은 실패**다.

## 실험 환경

| 항목 | 값 |
| --- | --- |
| 서버 | `http://localhost` |
| Workflow | `10200000-0000-0000-0000-000000000510` |
| Deployment | `10200000-0000-0000-0000-000000000610` |
| LLM node | `llm-request` |
| 실행 계정 | 데모 organization 관리자 계정 |
| 실행 수 | 50건 |
| 정책 점검 주기 | 10회 |
| 기본 모델 | `gpt-5.6-luna` |
| 제외 모델 | `gpt-5.6-sol` |
| 월간 검증 한도 | `$3` |

50개 입력은 같은 문장 틀의 값만 바꾼 데이터가 아니다. 단순 사용 안내, 계정·접근 권한, 재무 결산·지급 승인, 보안·개인정보 사고를 각각 다른 부서·역할·문장 구조로 작성하고, seed `270`으로 섞어 실행했다.

## 실제 처리 흐름

각 배포 실행에서는 다음 흐름이 정상적으로 진행됐다.

1. 배포 실행 API가 요청을 받았다.
2. RAG 검색과 LLM 호출이 수행됐다.
3. JSON 출력이 다음 노드와 호환되는 형태로 반환됐다.
4. workflow와 LLM node가 성공 상태로 종료됐다.
5. 비동기 task가 배포 실행을 정책 카운터와 관찰 테이블에 반영했다.
6. 10, 20, 30, 40, 50회에 정책 점검 task가 실행됐다.

실행 중에는 Judge LLM을 호출하지 않았다. 이 점은 runtime과 정책 갱신의 경계가 지켜졌다는 뜻이다.

## 정책 점검 결과

| 실행 수 | 정책 상태 | 정책 버전 | 갱신 후 결과 | 검증 batch |
| ---: | --- | --- | --- | --- |
| 10 | `collecting` | `bootstrap-preserve-config-v1` | `kept_current` | 없음 |
| 20 | `collecting` | `bootstrap-preserve-config-v1` | `kept_current` | 없음 |
| 30 | `collecting` | `bootstrap-preserve-config-v1` | `kept_current` | 없음 |
| 40 | `collecting` | `bootstrap-preserve-config-v1` | `kept_current` | 없음 |
| 50 | `collecting` | `bootstrap-preserve-config-v1` | `kept_current` | 없음 |

정책 점검 이력은 다섯 번 모두 생성됐다. 각 이력은 후보 Replay를 계획하려 했지만, 실제 batch를 만들 수 있는 입력군별 관찰 수가 부족해 현재 정책을 유지했다.

최종 active policy는 다음 의미의 상태였다.

```json
{
  "rules": [],
  "default_model_id": "gpt-5.6-luna",
  "fallback_model_id": null
}
```

`rules`가 비어 있으므로 입력군별 모델 선택은 일어나지 않는다. 모든 요청은 `default_model_id`인 `gpt-5.6-luna`로 실행됐다.

## 입력군 판정 분석

DB에는 운영 관찰 50건이 모두 저장됐다. 그러나 수동 입력군과 연결된 관찰은 다음 두 건뿐이었다.

| 입력군 | 기대 요청 수 | 연결된 관찰 수 |
| --- | ---: | ---: |
| 단순 사용 안내 | 12 | 0 |
| 계정·접근 권한 | 12 | 1 |
| 재무 결산·지급 승인 | 13 | 0 |
| 보안·개인정보 사고 | 13 | 1 |

수동 입력군 판정은 대표 문의 임베딩과 운영 문의 임베딩의 코사인 유사도가 `0.60` 이상이고, 두 번째로 가까운 입력군보다 `0.05` 이상 높아야 통과한다.

| 기대 입력군 | 가장 가까운 입력군이 정답인 건수 | 최종 기준 통과 건수 | 정답 입력군 유사도 평균 | 범위 |
| --- | ---: | ---: | ---: | --- |
| 단순 사용 안내 | 5/12 | 0 | 0.318 | 0.208~0.542 |
| 계정·접근 권한 | 8/12 | 1 | 0.404 | 0.297~0.780 |
| 재무 결산·지급 승인 | 12/13 | 0 | 0.433 | 0.247~0.575 |
| 보안·개인정보 사고 | 6/13 | 1 | 0.376 | 0.193~0.717 |

단순히 기준 `0.60`만 낮춰도 해결되지 않는다. 가장 가까운 입력군 자체가 정답인 요청이 31/50건이므로, 대표 문의 하나가 넓고 다양한 업무 표현을 충분히 대표하지 못한다.

## 후보 모델이 부족했던 것은 아니다

실험 organization에는 자동 라우팅 후보로 수집 가능한 모델이 여러 개 있었다.

- `gpt-5.4`
- `gpt-5.4-mini`
- `gpt-5-mini`
- `gpt-4.1`
- `gpt-4.1-mini`
- `gpt-4o-mini`
- `gpt-5.6-luna`

따라서 한 모델만 사용된 이유는 모델 카탈로그나 credential 부족이 아니다. 후보를 실제로 Replay 검증하기 위한 입력군별 운영 관찰이 모이지 않은 것이 원인이다.

## 코드 기준 원인

### 1. 입력군은 대표 문의 하나로 생성된다

데모 graph의 `cohort_drafts`는 입력군별 `representative_query` 하나를 저장한다. 첫 정책 생성 시 이 문장 하나의 임베딩이 입력군 중심점이 된다.

### 2. 운영 문의는 보수적인 기준으로 입력군에 연결된다

`AdaptiveModelRoutingCohortStore._match()`는 수동 입력군에 유사도 `0.60`, 1·2위 차이 `0.05`를 요구한다. 기준을 통과하지 못한 요청은 `unmatched`로 저장된다.

### 3. 후보 모델 하나를 검증하려면 같은 입력군의 관찰 5건이 필요하다

`ModelRoutingValidationPlanner.REPLAYS_PER_CANDIDATE`는 5다. `AdaptiveModelRoutingValidationService.plan_batch()`는 입력군에 연결된 최근 관찰이 5건보다 적으면 해당 입력군을 검증 계획에서 제외한다.

### 4. 검증 batch가 없으면 현재 정책을 유지한다

검증할 입력군이 없으면 정책 갱신 lease를 정상 종료하고 `kept_current`로 남긴다. 이때 active policy에 입력군 rule이 추가되지 않으므로 이후 요청도 기본 모델을 사용한다.

## 제품 보완안

### P0: 입력군 대표 예문을 내부적으로 여러 개 관리한다

사용자에게 문장 3~5개를 직접 입력하게 하면 설정 부담이 크다. UI에서는 지금처럼 대표 문의 하나만 요구하고, 입력군 마법사가 의미가 다른 합성 예문 3~5개를 생성해 `llm_node_model_routing_cohort_examples`에 저장하는 방식이 적절하다.

이미 테이블은 입력군별 여러 예문을 저장할 수 있지만, 현재 draft materialization은 대표 문의 하나만 생성한다. 여러 예문의 임베딩을 평균한 centroid 또는 예문별 최대 유사도 판정을 사용해야 한다.

### P0: 대표 예문 변경 후 기존 관찰을 재판정한다

운영 원문은 저장하지 않지만 관찰 임베딩은 저장돼 있다. 입력군 예문이 보강되면 기존 `unmatched` 관찰을 새 centroid에 다시 비교할 수 있다. 이렇게 해야 사용자가 같은 운영 요청을 다시 50번 보내지 않고도 검증을 시작할 수 있다.

### P1: 입력군별 판정 품질을 UI에 표시한다

다음 정보를 입력군 관리 화면에 보여주면 “왜 모델이 안 바뀌는지”를 사용자가 이해할 수 있다.

- 연결된 관찰 수 / 검증 시작 최소 5건
- 최근 판정 유사도 분포
- 기준 미달 요청 수
- 후보 Replay 준비 여부
- 마지막 검증 batch와 실패·보류 이유

### P1: 임계값은 전역 상수보다 입력군 증거로 조정한다

이번 결과에서 유사도 기준만 낮추면 서로 다른 입력군이 섞일 위험이 있다. 여러 대표 예문과 실제 정답 검증 데이터가 준비된 뒤 입력군별 precision을 지키는 범위에서 threshold와 margin을 조정해야 한다.
