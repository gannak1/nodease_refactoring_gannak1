# 놓치지 않는 AI 업무 메일 비서 시연 시나리오

## 1. 시연 개요

- **주제**: 수신 업무 메일의 우선순위 분류와 답변 초안 작성 자동화
- **목표 시간**: 4분 이내
- **핵심 메시지**: Nodease는 반복적인 메일 분류와 답변 초안 작성을 자동화하면서도, 중요한 답변의 최종 발송은 사람이 통제하고 실행 근거와 비용을 추적할 수 있게 한다.

업무 메일이 많아 단순 문의 사이에 장애·보안·개인정보 관련 긴급 메일이 묻히는 상황을 가정한다. 현업 담당자는 Agent Builder에 필요한 업무를 자연어로 설명하고, 생성된 workflow가 새 메일을 사내 대응 정책에 따라 세 등급으로 분류한다. 시스템은 답변 초안을 만들고 Slack으로 담당자에게 알리지만 고객에게 자동 발송하지 않는다.

## 2. 등급 분류 기준

| 등급 | 의미 | 예시 | 후속 처리 |
| --- | --- | --- | --- |
| 1등급 | 문서에 있는 내용으로 바로 답할 수 있는 단순 문의 | 사용 방법, 운영 시간, 일반 절차 | 일반 알림과 답변 초안 제공 |
| 2등급 | 담당자의 판단이 필요한 문의 | 환불, 예외 요청, 불만, 모호한 요구 | 검토 필요 표시와 답변 초안 제공 |
| 3등급 | 즉시 확인해야 하는 긴급 문의 | 장애, 보안, 개인정보, 법적 문제 | 긴급 표시와 즉시 확인 요청 |

LLM은 사내 `메일 대응 정책` Knowledge Base를 근거로 구조화된 분류 결과를 생성하고, 이후 Condition 노드가 등급 값에 따라 결정론적으로 경로를 선택한다.

## 3. 사전 준비

- 시연 전용 Gmail 계정과 발신자 계정을 준비한다.
- 받은편지함에는 시연 대상이 아닌 읽지 않은 메일이 없도록 정리한다.
- `메일 대응 정책` Knowledge Base에 등급 기준과 답변 원칙을 담은 문서를 색인한다.
- Gmail 조회 설정, 승인된 LLM credential, Knowledge Base, Slack 채널을 미리 연결한다.
- credential 원문이나 Gmail 앱 비밀번호는 발표 화면, 로그, 문서에 표시하지 않는다.
- 역할별 브라우저 탭과 workflow 실행 상세 화면을 미리 열어 둔다.
- Schedule Trigger를 사용할 경우 다음 실행 시각을 발표자와 메일 발송자가 공유한다.
- 외부 서비스 장애에 대비해 정상 실행 결과를 캡처하거나 예비 workflow 실행을 준비한다.

## 4. 4분 시연 흐름

### 1단계. 문제 제시 — 20초

**화면 조작**

- 업무 메일함과 여러 종류의 문의가 섞이는 상황을 간단히 보여준다.

**발표 문구**

> 여러분, 하루에도 수십 통씩 들어오는 업무 메일을 읽고 우선순위를 판단하고 답장까지 작성하느라 힘드시죠? 더 큰 문제는 단순 문의 사이에 정말 긴급한 메일이 묻힐 수 있다는 것입니다. Nodease가 이 과정을 어떻게 줄이는지 보여드리겠습니다.

### 2단계. 자연어로 workflow 생성 — 55초

Agent Builder에 미리 준비한 다음 요청을 입력한다.

```text
업무용 Gmail에서 읽지 않은 메일을 한 건 가져와 처리하는 워크플로우를 만들어줘.

메일 대응 정책 Knowledge Base를 근거로 다음과 같이 분류해줘.

1등급: 문서에 있는 내용으로 바로 답할 수 있는 단순 문의
2등급: 환불, 예외 요청, 불만처럼 담당자의 판단이 필요한 메일
3등급: 장애, 보안, 개인정보, 법적 문제처럼 즉시 확인해야 하는 긴급 메일

분류 결과는 등급, 한 줄 요약, 분류 이유, 답변 초안으로 작성해줘.
답변은 고객에게 자동으로 발송하지 말고 담당자가 검토할 수 있게 해줘.
처리 결과와 답변 초안을 Slack 담당 채널에 알리고,
3등급이면 긴급 표시를 포함해줘.
```

**발표 문구**

> 담당자는 메일 연결, LLM, 조건 분기 방법을 처음부터 설계하지 않고 필요한 업무를 자연어로 설명합니다.

### 3단계. 생성 결과 확인 — 30초

**화면 조작**

Preview Mode에서 다음 workflow 흐름을 짚는다.

```text
메일 조회
→ 대응 정책 KB를 사용하는 LLM 분류·답변 초안 생성
→ 등급별 조건 분기
→ Slack 알림
→ 처리 결과
```

승인된 Gmail 연결, Knowledge Base, LLM 모델, Slack 채널과 validation 상태를 확인한 뒤 `적용 및 저장`을 선택한다.

**발표 문구**

> Agent Builder가 메일 조회, 정책 기반 분류, 조건 분기와 알림으로 이어지는 초안을 만들었습니다. AI가 고객에게 답변을 임의로 발송하지 않고, 사람이 검토할 초안까지만 만드는 것이 이 workflow의 안전장치입니다.

**시연의 핵심 메시지**

> 자동화의 속도는 활용하되 외부 커뮤니케이션의 최종 책임은 사람에게 남깁니다.

### 4단계. 실시간 메일 처리 — 80초

**화면 조작**

1. 데모용 Gmail 받은편지함에 처리할 새 메일이 없는 것을 보여준다.
2. 다른 팀원이 아래의 긴급 문의 메일을 발송한다.
3. Schedule Trigger가 실행되거나 발표자가 준비된 테스트 실행을 시작한다.
4. Slack 담당 채널에 도착한 분류 결과와 답변 초안을 보여준다.

**메일 제목**

```text
긴급: 결제 완료 후 다른 고객 정보가 표시됩니다
```

**메일 본문**

```text
오늘 오전부터 결제를 완료하면 다른 고객의 주문 정보가 화면에 표시됩니다.
개인정보 문제일 수 있으니 즉시 확인 부탁드립니다.
현재도 같은 현상이 발생하고 있습니다.
```

**예상 Slack 알림**

```text
[3등급 | 긴급 확인 필요]

요약: 결제 화면에서 다른 고객 정보가 노출되는 현상
분류 이유: 현재 진행 중인 개인정보 노출 가능성이 있음
권장 조치: 보안 및 장애 대응 담당자에게 즉시 전달

답변 초안:
신고해 주셔서 감사합니다. 현재 관련 기능을 긴급 확인하고 있습니다.
추가적인 개인정보 입력을 중단해 주시고, 확인 결과를 안내드리겠습니다.
```

실제 결과 문구는 LLM 출력에 따라 달라질 수 있다. 발표자는 등급, 근거, 초안과 긴급 알림 전달 여부만 확인하고 문장 전체를 읽지 않는다.

**발표 문구**

> 방금 들어온 메일을 Nodease가 사내 대응 정책에 따라 3등급 긴급 메일로 분류했습니다. 담당자가 즉시 상황을 파악할 수 있도록 요약과 분류 이유, 검토 가능한 답변 초안까지 Slack으로 전달했습니다.

**시연의 핵심 메시지**

> 단순 문의를 줄이는 것뿐 아니라, 정말 중요한 메일을 놓치지 않게 하는 자동화입니다.

### 5단계. 실행 근거 확인 — 35초

**화면 조작**

Workflow 실행 상세에서 다음 항목만 빠르게 확인한다.

- Mail 노드의 정상 조회 여부
- LLM이 반환한 `3등급`과 안전한 분류 요약
- Condition 노드가 선택한 긴급 경로
- 사용한 정책 KB와 안전한 citation 요약
- Slack 전달 결과
- 실행 시간, 토큰과 실제 발생 비용

**발표 문구**

> 결과만 보여주는 것이 아닙니다. 왜 긴급으로 분류됐고 어떤 정책을 근거로 했으며, 어느 경로가 실행됐고 비용이 얼마나 들었는지도 확인할 수 있습니다. 민감한 credential과 불필요한 원문은 운영 기록에 그대로 남기지 않아야 합니다.

### 6단계. 마무리 — 20초

**발표 문구**

> Nodease를 사용하면 현업 담당자는 자연어 한 문장으로 메일 처리 workflow를 만들 수 있습니다. AI가 반복적인 분류와 초안 작성을 처리하고, 긴급한 메일은 즉시 알리며, 최종 발송 판단은 사람이 담당합니다. 자동화의 속도와 기업 운영에 필요한 통제를 함께 제공하는 것이 Nodease의 차별점입니다.

## 5. 기능 포함 범위

| 핵심 기능 | 시연 방법 |
| --- | --- |
| Agent Builder | 자연어 요청으로 메일 처리 workflow 초안을 생성한다. |
| Workflow Builder | Preview Mode에서 Mail, LLM, Condition, Slack 노드를 확인한다. |
| LLM credential/model | 승인된 연결과 모델을 사용하며 secret은 표시하지 않는다. |
| Knowledge/RAG | 사내 메일 대응 정책을 근거로 분류와 초안을 생성한다. |
| Workflow Runtime | 새 메일을 입력으로 실제 workflow를 실행한다. |
| 조건 분기 | LLM의 구조화된 등급에 따라 결정론적으로 알림 경로를 선택한다. |
| 외부 연동 | Gmail을 조회하고 Slack에 처리 결과를 전달한다. |
| Audit/Trace | 노드별 실행 결과, 사용 근거와 전달 상태를 확인한다. |
| Usage/Cost | 해당 실행에서 실제 발생한 토큰과 비용만 보여준다. |

누적 데이터가 필요한 조직 예산 위험과 A/B 비용 최적화는 이 시연에서 제외한다. Organization/RBAC은 연결 가능한 Gmail, KB, Slack 채널의 범위를 제한하는 기반으로 적용하되, 4분 안에 별도 권한 신청 절차까지 시연하지 않는다.

## 6. 현재 구현 기준 시연 범위

### 현재 기능으로 구성할 수 있는 흐름

- Mail 노드가 IMAP으로 Gmail의 읽지 않은 메일을 조회한다.
- LLM 노드가 정책 KB를 사용해 등급과 답변 초안을 생성한다.
- Condition 노드가 등급에 따라 경로를 선택한다.
- Slack 노드가 담당 채널에 분류 결과와 답변 초안을 전달한다.
- 실행 상세에서 trace, citation, 토큰과 비용을 확인한다.

### 현재 흐름에서 주의할 제약

- Mail 노드는 메일 도착 event trigger가 아니라 IMAP 검색 노드다. 자동 실행은 Schedule Trigger 기반 polling으로 설명해야 한다.
- Mail 노드는 Gmail 임시보관함에 답장 초안을 생성하지 않는다. 현재 시연에서는 답변 초안을 Slack과 Nodease 실행 결과에 표시한다.
- Nodease 내부 notification은 일반 workflow 알림 채널이 아니므로 이번 시연에서는 Slack을 사용한다.
- 외부 연동 노드는 Agent Builder가 구조를 생성하더라도 credential과 대상 채널을 사용자가 확인하고 설정해야 한다.
- 자동 생성된 graph는 Mail 출력 mapping, LLM 구조화 출력, Condition source handle과 Slack 설정이 runtime 계약에 맞는지 사전 검증해야 한다.

## 7. Gmail 임시보관함 저장을 위한 후속 구현

Gmail 임시보관함에 실제 답장 초안을 생성하는 완성형 시나리오에는 다음 기능이 필요하다.

- Google OAuth 기반 Gmail credential 관리
- Gmail `users.drafts.create` 전용 workflow node 또는 안전한 connector adapter
- 원본 발신자, 제목과 thread 식별자를 보존한 reply draft 생성
- 처리한 Gmail message ID의 durable idempotency 관리
- Slack 알림과 draft 생성의 부분 실패 상태 및 재시도 정책
- 전체 후속 처리가 성공한 뒤에만 메일을 처리 완료로 전환하는 상태 관리
- credential과 메일 원문을 제외한 redaction-safe Audit/Trace 정책

범용 HTTP 노드에 Gmail access token을 직접 입력해 drafts API를 호출하는 구성은 credential 저장과 trace 노출 위험 때문에 사용하지 않는다.

## 8. 중복 처리와 실패 경계

현재 Mail 노드의 읽음 처리만으로 운영 수준의 중복 방지를 보장할 수 없다.

- 조회 즉시 읽음 처리하면 후속 LLM 또는 Slack 단계가 실패해도 메일이 처리된 것처럼 남을 수 있다.
- 읽음 처리하지 않으면 다음 Schedule 실행에서 같은 메일이 다시 처리될 수 있다.
- 운영 구현은 Gmail message ID를 idempotency key로 저장하고 terminal 성공 이후 처리 완료 상태를 기록해야 한다.
- 부분 실패는 재시도 가능 여부와 성공한 단계가 구분되어야 하며 같은 Slack 알림이나 draft가 중복 생성되지 않아야 한다.

이번 단발성 시연에서는 전용 받은편지함에 메일을 한 건만 넣고, 성공 후 Schedule 배포를 중지하거나 테스트 실행을 한 번만 수행한다. 이 설정을 운영 가능한 자동화라고 설명하지 않는다.

## 9. 시연 안정성 점검

- Gmail IMAP 접근과 Slack 전달을 동일한 시연 환경에서 미리 검증한다.
- 데모 Gmail 받은편지함의 읽지 않은 메일을 모두 정리한다.
- Schedule Trigger의 다음 실행 시각과 서버 timezone을 확인한다.
- 발신 담당자는 정해진 제목과 본문을 즉시 전송할 수 있도록 준비한다.
- LLM 출력이 `grade`, `summary`, `reason`, `reply_draft` 구조를 지키는지 확인한다.
- Condition의 세 branch가 각각 정확한 output handle에 연결되어 있는지 확인한다.
- Slack 대상 채널과 credential 설정이 `unresolved` 상태로 남지 않았는지 확인한다.
- 메일 또는 답변 원문, credential, token이 trace나 발표 화면에 불필요하게 노출되지 않는지 확인한다.
- Agent Builder가 지연되면 사용할 저장 완료 workflow를 예비 탭에 준비한다.
- Gmail, LLM 또는 Slack 장애에 대비해 동일 실행의 캡처 화면을 준비한다.

## 10. 시간 초과 시 생략 순서

1. Preview에서 개별 노드 설정 설명을 생략한다.
2. Slack 답변 초안 전체를 읽지 않고 등급과 요약만 확인한다.
3. Trace에서 Mail·Condition·Slack 세 노드만 확인한다.
4. 토큰과 비용은 숫자만 짚고 상세 화면 설명을 생략한다.
