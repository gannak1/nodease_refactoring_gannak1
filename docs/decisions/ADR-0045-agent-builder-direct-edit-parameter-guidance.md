# ADR-0045: Agent Builder direct edit and parameter guidance

Status: Accepted

Related ADRs: [ADR-0019](ADR-0019-agent-builder-preview-apply-save-boundary.md), [ADR-0024](ADR-0024-agent-builder-node-capability-catalog.md), [ADR-0025](ADR-0025-agent-builder-intent-model-selection.md), [ADR-0026](ADR-0026-agent-builder-intent-and-connection-validation.md), [ADR-0027](ADR-0027-agent-builder-pre-intent-safe-kb-context.md), [ADR-0040](ADR-0040-agent-builder-unified-model-recommendation.md), [ADR-0046](ADR-0046-agent-builder-graph-mutation-and-cas-save.md), [ADR-0054](ADR-0054-agent-builder-generation-modes.md)

## Context

Agent Builder MVP는 서버가 draft preview를 만들고 사용자가 `적용 및 저장`을 선택한 뒤에만 workflow graph를 변경한다. 이 경계는 저장 전 권한 재확인과 stale 검사를 명확하게 만들지만, graph 생성과 node 설정을 한 번에 확정해야 하므로 다음 문제가 생긴다.

- 설정이 부족한 node를 만들기 위해 여러 종류의 clarification이 Agent Builder message 계약에 계속 추가된다.
- parameter의 정의, 입력 UI, graph 연결 추천이 planner 응답과 frontend 조건문에 분산된다.
- 사용자는 preview와 실제 editor를 오가며 node를 확인해야 하며, 생성 직후 기존 node panel에서 값을 채우는 흐름과 단절된다.
- parameter마다 자연어를 다시 구조화하면 비용과 지연이 커지고, catalog와 runtime 계약보다 LLM 추론이 우선될 위험이 있다.

Workflow editor에는 graph snapshot 기반 Undo/Redo가 이미 있다. Node Capability Catalog도 node 지원 여부, 연결 정책, 필수 설정을 제공한다. 따라서 Agent Builder가 안전한 `GraphMutation`을 만들고 editor가 이를 하나의 history transaction으로 적용한 뒤, catalog 기반 parameter task를 순차 처리하는 구조가 더 응집도가 높다.

## Decision

MBA-228은 다음 목표 구조를 채택한다.

1. Agent Builder direct-edit는 설정을 확인하며 만드는 흐름과 구조만 생성하는 흐름을 지원한다. MBA-228 당시 mode 값은 `configure_and_generate|structure_only`였으며, 현재 canonical mode와 기본값, 빠른 생성 eligibility 및 mode 전환은 ADR-0054가 소유한다.
2. planner LLM은 사용자 요청을 한 번 구조화해 node 목적, graph 의도, parameter가 필요한 이유에 대한 안전한 설명을 만든다. Parameter 설명 hint는 `step_id`, Catalog가 prompt에 제공한 `parameter_key`, `reason`, `input_guidance`로 제한한다. Backend는 step capability의 Catalog에 존재하는 key만 사용하고 잘못된 hint는 폐기한 뒤 Catalog 설명으로 fallback한다. 실제 parameter key, 타입, 필수 여부, 검증 규칙은 Node Capability Catalog가 결정한다.
3. backend는 완성 graph snapshot 대신 base graph hash와 workflow `updated_at`을 전제로 한 typed `GraphMutation`과 parameter task 목록을 반환한다.
4. frontend editor adapter는 Agent Builder 시작 전 graph snapshot과 acknowledgement가 끝난 최종 graph를 하나의 Workflow history boundary로 관리한다. 최초 `initial_graph`, `graph_edit` 또는 `replace_workflow`가 boundary를 만들고 이후 `parameter_update`와 `knowledge_binding`은 graph를 CAS 저장하되 별도 Workflow history entry를 만들지 않고 같은 boundary의 final snapshot/hash만 갱신한다. 생성 완료 뒤 수동 editor 변경은 일반 history entry로 boundary 뒤에 쌓이므로 먼저 Undo된다.
5. `설정하며 생성`에서는 catalog에 정의된 모든 configurable parameter에 task record를 만들고 node별 카드 그룹으로 표시한다. 최초 structural GraphMutation이 acknowledgement되기 전에는 모든 task를 `pending`으로 유지하고 decision endpoint도 제출을 거부한다. Acknowledgement 뒤에만 첫 task를 `active`로 전환한다. 자동 추천값은 graph에 먼저 반영하고 `resolution_source=user_request|existing_graph|upstream_selector|catalog_default`를 남기지만, 사용자가 확인하거나 수정하기 전까지 task를 `pending|active`로 유지한다. `user_request`는 같은 발급 흐름에서 실제 값이 GraphMutation에 materialize된 경우에만 사용한다. ADR-0054의 quick-to-guided 전환처럼 실제 값을 저장하지 않은 복구 경로는 `resolution_source=null`, `reconfirmation_required=true` task로 다시 입력받고 원 prompt나 replica memory에서 값을 복원하지 않는다. 값이 변하지 않은 확인은 관련 structural operation이 `acknowledged`이고 canonical graph 값이 일치할 때만 멱등 `confirm` action으로 처리하며 GraphMutation이나 workflow 저장을 반복하지 않는다. 수정은 같은 task의 `set` action이 새 `parameter_update` GraphMutation, CAS 저장과 acknowledgement를 거쳐 `completed`가 된다. 현재 입력 task의 node를 canvas 중앙에 focus하고, 값은 일반 chat message가 아닌 타입별 control로 입력한다.
6. 이전 node의 output과 현재 node의 input 계약에서 만들 수 있는 selector는 deterministic resolver가 추천한다. LLM이 임의의 JSON path나 credential 값을 생성하지 않는다. 기존 graph 수정의 `between` 요청은 선택된 edge 또는 자연어로 식별한 source/destination node 쌍만 대상으로 한다. 자연어 node 쌍은 server-loaded graph의 직접 edge가 정확히 하나일 때만 삽입 위치로 확정한다. 직접 edge가 없거나 둘 이상이면 임의 선택하지 않고 기존 edge 선택 clarification으로 닫는다. 여러 hop 경로 탐색은 이 ADR의 범위가 아니다.
7. `구조만 생성`은 `generation_mode=structure_only`로 표현하고 parameter task를 열지 않는다. 빈 workflow의 신규 생성은 `initial_graph`, 기존 workflow의 부분 구조 변경은 `graph_edit`, 비어 있지 않은 editor에서 완결된 신규 workflow를 생성하거나 명시적으로 전체 교체하면 `replace_workflow` GraphMutation을 사용한다. `replace_workflow`는 기존 edge/node 전체를 제거하고 새 node/edge를 추가하는 typed operation 묶음이며 raw graph payload를 허용하지 않는다. Generation mode와 mutation kind는 독립이고 unresolved external-action configuration은 실행·배포 preflight가 계속 차단한다.
8. Knowledge Base 선택, 자동 추천 확인과 수동 parameter 입력은 하나의 workflow 설정 결과 UI에서 순차 처리한다. 같은 Knowledge requirement에 legacy clarification과 direct-edit 설정 card를 동시에 표시하지 않는다. Knowledge Base 선택이 node 종류나 graph topology를 바꾸면 통합 UI의 첫 단계인 `before_graph`, 기존 node binding만 바꾸면 graph 생성 뒤 같은 UI의 `after_graph`로 처리한다. `before_graph` 후보를 하나도 선택하지 않은 제출은 별도 가짜 후보나 재질문 없이 KB 없이 생성하겠다는 명시적 결정이다. Direct response의 `knowledge_resolution`은 후보 유무와 무관한 상위 `resolution_id`를 가지며 candidate가 처음부터 0개여도 같은 설정 card와 empty-selection CTA를 표시한다. Planner는 선택별 완성 graph를 만들지 않고 requirement id, timing, target step, effect kind와 Knowledge step/upstream/downstream/empty-selection bridge policy로 구성된 typed Knowledge placement만 반환한다. Backend는 KB와 무관한 base topology와 이 placement를 Catalog로 검증한 뒤 선택이 있으면 Knowledge 의존 node/data/edge를 구성하고 빈 선택이면 bridge policy에 따라 이를 생략한다. 여러 KB는 같은 requirement의 binding 목록으로 처리하며 선택 뒤 자연어 요청이나 planner를 다시 호출하지 않는다. 선택 graph와 KB-free graph 중 해당 제출 결과가 유효하지 않으면 부분 저장 없이 validation failure로 닫는다.
9. raw secret, token, API key, credential config는 planner prompt, chat transcript, parameter task 설명, audit metadata에 포함하지 않는다. credential 연동은 safe credential reference만 허용하며 원문 입력 지원은 별도 이슈로 남긴다.
10. graph 생성 중 workflow 실행, retrieval, 외부 action 실행, credential 사용 또는 외부 시스템 변경은 발생하지 않는다.
11. 최초 graph 생성, 기존 graph 구조 변경, 전체 workflow 교체, parameter decision과 `after_graph` Knowledge binding은 ADR-0046의 공통 `GraphMutation`을 사용한다. Local 적용 뒤 `operation_id`, expected base graph hash와 expected workflow `updated_at`을 포함한 CAS workflow draft 저장을 수행하고, server가 반환한 canonical graph hash와 `updated_at`으로 acknowledgement한다. Agent Builder 저장, 일반 autosync, version 복원, test 전 저장과 Undo/Redo는 같은 frontend canonical metadata 상태를 읽고 모든 성공한 draft GET/POST 결과로 이를 갱신한다. Server는 acknowledgement 전에는 operation, parameter task 또는 Knowledge selection을 완료하거나 다음 task를 활성화하지 않는다.
12. MBA-228 parameter/input/output 계약은 Workflow Node Capability Catalog v3로 도입한다. Phase 1에서 단일 bundled catalog, parser와 backend/frontend parity test를 함께 v3로 전환한다. Full typed `operations`는 발급 API 응답에서만 client에 전달하고 DB/session payload에는 저장하지 않는다. 기존 `AgentBuilderRequest.response_payload`에는 `catalog_version=3`, operation id/kind/status, base graph hash, 발급 시 server가 candidate를 검증해 계산한 `expected_result_graph_hash`, expected workflow `updated_at`, affected node ids와 completion context로 구성된 safe operation envelope만 저장한다. 버전이 없거나 `2`인 미적용 operation은 legacy stale로 분류해 재생성을 요구하며, `3`인 envelope만 CAS 저장·acknowledgement 후보가 된다. Catalog version이나 operation 원문을 위한 별도 column/table, encrypted operation store 또는 legacy backfill은 만들지 않는다.
13. Direct-edit는 MBA-228의 단일 기능 PR에서 additive protocol migration과 mixed-version read로 전환한다. Nullable `AgentBuilderSession.protocol_version`을 추가하고 신규 direct-edit session에는 `direct_edit_v1`을 기록한다. 기존 null session은 backfill하거나 자동 변환하지 않고 legacy Preview session으로 판별해 `stale_protocol`로 복구한다. Preview API/UI는 direct-edit parity와 필수 integration/E2E 검증을 통과한 뒤 제거한다. `generation_mode`는 request마다 선택할 수 있으므로 request `response_payload`에만 저장한다. MBA-228의 기존 `configure_and_generate` 값은 ADR-0054에 따라 canonical `guided_generate`로 읽기 정규화하며 기존 row를 backfill하지 않는다. Frontend와 Gateway의 무중단 전환, 단계적 rollout/rollback, 배포 gate와 image 산출물 분리는 별도 배포 결정의 범위다.
14. GraphMutation의 `configuration_state=unresolved` 외부 action node는 저장할 수 있지만 server-side 실행과 배포 preflight에서 차단한다. Mutation 발급, CAS 저장, 차단과 acknowledgement는 safe metadata만 audit한다.
15. 모든 graph 저장과 acknowledgement가 완료되어 Agent Builder 결과가 완료 상태가 된 뒤 Workflow Undo가 boundary에 도달하면, configurable ParameterTask가 있는 경우 첫 Undo는 graph를 바꾸지 않는 parameter 재진입 단계다. 재진입 대상은 수동 설정 여부와 관계없이 `completed|skipped|deferred` 중 재편집 가능하고 `stable_order`가 가장 큰 task다. 이때 persisted task status/version과 graph 값은 변경하지 않고 client presentation에서만 해당 task를 현재 편집 대상으로 표시한다. Agent Builder panel이 닫혔거나 최소화돼 있으면 열고 최소화를 해제하며, 대상 node를 선택해 panel을 제외한 가시 canvas 영역에서 가리지 않는 가장 큰 배율로 focus하고 해당 card를 보이게 scroll한다. 첫 Undo 직후 input control로 keyboard focus를 강제하지 않아 다음 canvas Ctrl+Z가 전체 복구로 이어질 수 있게 한다. completed/skipped/deferred task 사이의 이동은 Workflow Undo가 아니라 ParameterTask UI의 `이전 항목` control이 담당한다. 재진입 상태에서 다음 Workflow Undo는 Agent Builder 시작 전 snapshot을 CAS 저장하고 생성 node/edge, parameter 값과 Knowledge binding을 포함한 결과 전체를 제거하며 모든 ParameterTask와 Knowledge resolution을 `canceled`로 닫는다. Task가 없으면 완료 상태의 첫 Undo가 바로 전체 복구다. `replace_workflow` boundary의 시작 snapshot은 교체 전 graph 전체다. Graph 저장 또는 acknowledgement가 끝나지 않은 결과는 완료 상태 Undo로 취급하지 않는다.
16. 전체 복구 뒤 reload 전 Ctrl+Y 또는 Ctrl+Shift+Z는 client memory의 최종 graph snapshot을 다시 적용하고 서버 graph를 CAS 저장하지만 canceled ParameterTask나 Knowledge 흐름을 재실행하지 않는다. 전체 Redo 뒤 같은 client memory에서 다시 Undo하면 canceled task UI에 재진입하지 않고 시작 전 graph로 바로 CAS 복구한다. Parameter 재진입 단계에서 Redo는 graph를 바꾸지 않고 설정 UI를 닫아 완료 표시로 돌아간다. Redo stack과 parameter 재진입 표시는 client memory 전용이며 reload 뒤 복구하지 않는다. Parameter input의 Ctrl+Z는 control 내부 text history만 사용하고 Agent Builder card/button focus에서는 canvas Undo/Redo command를 실행하지 않는다.
17. Catalog v3의 각 parameter는 `defer_policy=forbidden|allow_unresolved`를 가진다. 값이 없으면 `forbidden`으로 해석한다. Required parameter의 `forbidden`은 frontend에 defer control을 제공하지 않고 backend도 defer를 거부한다. `allow_unresolved` defer는 `parameter_update` GraphMutation, CAS 저장과 acknowledgement 뒤 task를 `deferred`로 전환하고 다음 task로 진행한다. Optional `skip`은 defer와 별도이며 graph 값을 만들지 않고 operation id와 expected task version 검증 뒤 task를 명시적 `skipped` 상태로 전환한다. Skipped task를 다시 열어 값을 설정하면 일반 `parameter_update`/CAS/acknowledgement를 거쳐 `completed`가 된다. Parameter flow 전체 취소는 남은 task를 `canceled`로 닫고 이미 저장된 graph는 유지한다. Node `configuration_state`는 마지막 task action이 직접 지정하지 않는다. Backend가 Catalog의 모든 required configuration을 생성, set/defer/skip/Undo/복구와 실행·배포 preflight마다 다시 계산하며 하나라도 missing/deferred/invalid이면 `unresolved`, 모두 유효할 때만 `resolved`다. Client가 이 값을 권위 있게 설정할 수 없다.
18. Parameter decision은 client-generated `operation_id`와 expected task version을 포함한다. Backend는 parent request row를 잠그고 target task/version과 action별 허용 상태를 확인한 뒤 첫 decision만 처리한다. 자동 추천값의 `confirm`은 canonical graph 값과 발급된 recommendation context가 변하지 않았을 때만 `active` task를 GraphMutation과 workflow 저장 없이 `completed`로 전환하고 다음 task를 활성화한다. 같은 confirm operation 재시도는 같은 결과를 반환한다. 값 설정 `set`은 `active|completed|skipped|deferred|invalid` task에 허용하며 유효한 값의 acknowledgement가 끝난 뒤에만 `completed`로 전환한다. Catalog validation이 실패한 `set`도 operation id, payload fingerprint와 safe invalid 결과를 기록하며 같은 제출 재시도에는 최초 invalid 결과를 반환하고 audit와 task version을 반복 변경하지 않는다. `pending`은 순차 진행으로 active가 된 뒤 처리하고 `canceled`는 다시 편집하지 않는다. 다른 동시 decision은 `task_conflict`로 거부하며 GraphMutation이나 다음 task를 중복 생성하지 않는다. 기존 `AgentBuilderRequest.response_payload` JSON은 nested object를 제자리 변경하지 않고 전체 새 객체를 재할당해 저장한다.
19. `previous`는 canonical task status/version, workflow graph와 Workflow history를 변경하지 않는 client-only navigation이다. 현재 presentation task가 canonical `active|completed|skipped|deferred`인 경우 backend는 stable order상 이전 재편집 가능 task를 `next_task_id`로 반환하고 frontend는 이를 presentation cursor로 소비해 card, node selection과 focus를 이동한다. `previous`로 이동한 뒤에는 새 card heading으로 접근성 focus를 옮기되 input 값을 자동 변경하지 않는다.
20. ParameterTask를 다시 표시할 때 실제 값은 canonical workflow graph와 Catalog parameter mapping에서 읽어 typed input의 일시적 초기값으로 사용한다. 값은 task/session/audit payload에 복제하지 않는다. `skipped|deferred` task에 graph 값이 없으면 빈 control을 표시한다. Credential/resource reference는 현재 사용자 권한으로 다시 조회 가능한 safe opaque reference만 표시하며, 권한을 잃었거나 삭제된 reference는 ID와 label을 노출하지 않고 사용할 수 없는 기존 설정으로 표시한다. Raw secret, token과 API key는 복원하거나 표시하지 않는다.

완료 상태는 모든 필수 Knowledge 선택과 parameter 확인, 관련 graph 저장과 acknowledgement가 끝난 뒤에만 명시적으로 표시한다. 이 조건을 충족하지 않은 결과에는 완료 history boundary Undo를 허용하지 않는다.

자동 추천값은 원문이 아닌 canonical SHA-256 `recommendation_fingerprint`를 safe task metadata에 남긴다. `confirm`은 canonical graph 값의 fingerprint와 발급 fingerprint가 일치할 때만 허용하며 fingerprint에 secret 또는 값 원문을 저장하지 않는다.

원래 mutation 제출 흐름에서 acknowledgement 응답만 유실되면 client는 같은 `operation_id`와 canonical metadata로 acknowledgement를 정확히 한 번 재시도할 수 있다. 그 재시도 뒤 또는 직접 session 조회, pending request polling, acknowledgement 확인 중 transport 또는 5xx 오류가 발생하면 client는 acknowledgement를 다시 전송하지 않고 같은 session context를 삭제하지 않은 채 `1초 -> 2초 -> 4초` 간격으로 최대 세 번 session 조회만 자동 확인한다. 세 번 모두 결과가 불명확하면 `결과 확인 필요` 상태와 명시적 `다시 확인` control을 표시한다. 사용자가 다시 확인을 선택하면 새 세 번의 session 조회 구간만 시작하며, 자연어 요청, planner, GraphMutation 또는 acknowledgement를 추측하여 재실행하지 않는다. `stale_protocol`, server가 명시한 session not found 또는 invalid session만 local session pointer를 제거하고 새 direct-edit session 전환을 허용한다.

21. Mail/Gmail처럼 runtime이 관리 credential reference를 요구하고 organization-scoped use 권한 resolver가 존재하는 provider만 `credential_ref` task와 permission-filtered picker를 제공한다. Gmail Draft에는 `provider=gmail`, `auth_type=oauth2`인 use-permitted credential만 후보와 제출 대상으로 허용한다. Slack/GitHub는 MBA-228 direct-edit의 credential task, picker, token 입력, `defer` 대상이 아니다. Agent Builder는 Slack/GitHub node를 `configuration_state=unresolved`로 생성하고 동일 workflow 설정 결과에서 node별 `연결 설정으로 이동` action만 제공한다. 이 action은 대상 node와 기존 Editor의 연결/인증 control을 열 뿐 credential API, GraphMutation, workflow save, planner 또는 외부 action을 호출하지 않는다. Slack/GitHub의 안전한 reference binding과 provider 권한 model이 실제로 도입되면 Agent Builder 지원 여부를 별도 ADR에서 다시 결정한다. unresolved 외부 action node는 저장할 수 있으나 server preflight가 test, run, deployment를 차단한다.
22. `direct_edit_v1` Knowledge 후보는 `knowledge_resolution.candidates`와 전용 Knowledge selection endpoint로만 반환·제출한다. Candidate가 비어 있어도 상위 `resolution_id`로 empty selection을 제출한다. Frontend와 selection service는 `clarification_options`를 direct 후보 fallback으로 읽지 않고, 같은 후보를 `clarification_options`에 중복 반환하지 않으며 message endpoint의 legacy `selected_knowledge_candidate(s)` 입력은 거부한다. 같은 resolution이 `pending_ack|completed`이면 legacy/direct 교차 제출이나 중복 operation을 허용하지 않는다. Catalog의 `llmNode.knowledgeBases`는 저장 graph binding의 schema로만 사용하고 direct-edit에서는 일반 `resource_ref` ParameterTask 또는 별도 후보 picker를 만들지 않는다. 이전 direct-edit session에 저장된 같은 generic task는 session 복구 시 제거하고 남은 task를 다시 순차 상태로 정리한다.
23. Knowledge 선택 중에는 하나의 설정 card와 선택값을 유지하고 save/acknowledgement 성공 뒤에만 대화형 선택 결과를 확정한다. 실패는 같은 card에서 재시도할 수 있고 결과가 불명확하면 canonical session의 안전한 `messages`와 `knowledge_resolution`을 다시 hydrate해 `unapplied|pending_ack|completed`를 판정한다. `unapplied`는 같은 card와 선택값으로 재시도하고, `pending_ack`는 control을 잠근 채 reconciliation을 계속하며, `completed`는 선택 card를 닫고 다음 설정 또는 완료 단계로 진행한다. Frontend 실패 경로는 canonical session read를 수행하고, `before_graph` structural operation의 typed payload가 저장 전에 유실되면 server는 연결된 Knowledge resolution을 `unapplied`로 되돌려 같은 card에서 새 operation으로 재시도하게 한다. 자연어 요청이나 planner를 다시 호출하지 않고 응답에서 유실된 typed operations도 재생하지 않는다.
24. 완료 task의 수정은 result group의 명시적 `editing` presentation 상태다. 편집 중에는 완료 표시를 숨기고 active task 유무와 관계없이 취소/닫기를 제공하며 실패 시 입력값을 유지한다. Acknowledgement 뒤에만 편집을 닫고 완료 상태로 돌아간다. 자동 추천 출처는 `user_request=사용자 요청에서 확인`, `existing_graph=기존 Workflow 설정 사용`, `upstream_selector=이전 노드 출력에서 연결`, `catalog_default=기본값 추천`의 safe 문구로 표시한다. `existing_graph`는 Agent Builder 시작 전 canonical base graph에 있던 node의 실제 설정값에만 사용한다. mutation이 추가한 node의 template/default 값은 `catalog_default`, server가 확정한 upstream selector는 `upstream_selector`로 표시한다. Knowledge recommendation reason은 allowlisted 사용자 문구로만 표시하고 알 수 없는 내부 enum은 원문을 노출하지 않는다.
25. Knowledge CTA는 timing을 반영한다. `before_graph`는 `선택한 Knowledge Base로 생성`/`Knowledge Base 없이 생성`, `after_graph`는 `선택 적용`/`Knowledge Base 없이 계속`을 사용한다.
26. 완료 boundary 첫 Undo의 재진입 대상은 status와 최대 `stable_order`만으로 선택한다. `secret_forbidden`, `credential_ref`, provider 또는 node type을 이유로 제외하지 않는다. Raw secret과 권한을 잃은 reference 차단은 graph hydration/rendering 경계가 담당한다. Session reload와 `stale_protocol` 전환은 만료되지 않은 request의 redaction을 통과한 안전한 대화 이력을 시간순으로 복구한다. `stale_protocol`에서는 legacy graph/draft/apply를 폐기하고 안전한 대화만 읽기 전용으로 유지한다.
27. Agent Builder가 `conditionNode` 뒤의 edge를 생성할 때 모든 outgoing edge는 case id 또는 `default`인 명시적 `sourceHandle`을 가져야 한다. 생성기가 만든 단일 선형 downstream edge만 mutation 발급 전에 downstream node를 보존한 채 `default` handle로 명시화하며, handle 없는 edge가 여러 개이거나 이미 explicit default와 충돌하면 target을 추측하지 않고 validation failure로 닫는다. Backend는 동적인 case 목록과 default 각각에 대해 기존 node 또는 `연결 안 함`을 선택하는 typed ParameterTask를 만들고, 기존 explicit edge의 target은 control 초기값으로 hydrate하되 사용자가 branch decision을 확인하기 전에는 Condition configuration을 `unresolved`로 계산한다. `cases` 변경 acknowledgement 뒤에는 canonical graph의 case/default handle과 task를 재조정해 새 handle을 pending으로 추가하고 제거된 handle을 canceled로 보존한다. `연결 안 함`은 명시적으로 확인된 terminal decision이며 해당 handle edge를 만들지 않는다. Validator와 Workflow runtime은 같은 handle 계약을 사용하고 handle 없는 edge를 암묵적 default로 해석하지 않는다.

## Authority And Migration

이 ADR은 MBA-228 Agent Builder direct-edit parameter/Knowledge UX와 history boundary의 Accepted authority다. 생성 mode, 기본값, 빠른 생성 eligibility와 mode 전환은 ADR-0054가 보완해 소유한다. ADR-0046은 GraphMutation/CAS 저장을 구체화하는 supporting authority이며 ADR-0019는 Superseded legacy 기록이다. Preview 결과는 characterization fixture로만 고정하고 direct-edit parity와 필수 integration/E2E를 통과한 뒤 API/UI 분기를 제거한다.

저장 전 권한, stale, validation, audit 정책 자체는 폐기하지 않는다. Frontend는 모든 Agent Builder GraphMutation을 local history transaction으로 적용한 뒤 CAS workflow draft 저장을 완료해야 한다. Backend는 저장된 canonical graph hash와 workflow `updated_at`을 확인한 acknowledgement 이후에만 operation 완료, parameter task 전환 또는 Knowledge binding 확정을 기록한다. Direct-edit graph는 일반 editor save endpoint의 additive mutation context를 사용하며 실행·배포 preflight는 별도로 유지한다.

MBA-228에서는 Agent Builder를 별도 서버로 분리하지 않는다. Gateway 내부에서 application, DB adapter, composition 경계를 분리하고 기존 service는 전환 facade로 유지한다. 별도 서버, 신규 Agent Builder table, 전체 schema 파일 분할은 후속 계획으로 관리한다.

MBA-228은 하나의 기능 PR에서 nullable protocol migration, null/`direct_edit_v1` mixed read, legacy `stale_protocol` 복구와 direct-edit parity 뒤 Preview 제거를 구현하고 contract·migration·integration·E2E test를 제공한다. Alembic single head와 기존 DB upgrade를 확인하며 legacy row를 backfill하거나 additive schema를 downgrade하지 않는다. Frontend와 Gateway가 서로 다른 revision으로 배포되는 동안의 프로토콜 호환성, staged rollout/rollback, creation gate와 immutable image 증거는 별도 배포 ADR과 후속 이슈에서 다룬다.

## Consequences

- backend orchestration은 intent planning, capability resolution, GraphMutation generation, parameter task planning으로 분리된다.
- frontend의 Agent Builder panel은 conversation과 task presentation을 담당하고 graph mutation은 workflow store adapter에 위임한다.
- Node Capability Catalog는 단순 allowlist를 넘어 parameter schema와 input/output 계약의 권위가 된다.
- Undo가 rollback UX를 제공하지만 저장 전 권한과 stale 검사는 GraphMutation 발급 시점, 최초 CAS save와 persisted revert save 경계에서 계속 필요하다.
- 기존 Preview Mode 결과는 characterization fixture로만 사용하고 전용 API와 UI는 direct-edit 저장·복구 검증을 통과한 뒤 제거한다. Preview를 수정·확장하거나 활성 fallback으로 유지하지 않으며 한 session에서 preview 방식과 direct-edit 방식을 혼용하지 않는다.
- parameter 설명 품질은 planner가 담당하지만 값의 유효성이나 실행 가능성은 catalog와 runtime validator가 담당한다.
- Parameter task 상태와 workflow graph 값은 canonical graph hash와 workflow `updated_at` acknowledgement를 기준으로 함께 전진하므로 저장 실패나 새로고침 뒤 서로 다른 완료 상태로 복구되지 않는다.

## Non-Goals

- credential 원문을 Agent Builder가 수집하거나 저장하는 기능
- workflow 생성 중 node 실행 또는 외부 action 실행
- runtime에 없는 node capability 추가
- 모든 node panel을 Agent Builder 전용 UI로 복제
- parameter마다 별도 LLM 호출
- 일반 workflow editor의 기존 권한 모델 변경. 단, unresolved 외부 action의 실행·배포 preflight 차단은 MBA-228 범위다.
- Agent Builder의 독립 서버 또는 독립 데이터베이스 도입
- Agent Builder intent model 표시 순서 변경
- Frontend와 Gateway의 무중단 coordinated rollout, 배포 gate, staged rollback과 image artifact 검증

## 2026-07-14 Correction: LLM Knowledge Selection And Input Continuity

- canonical `generation_mode=guided_generate`의 일반 LLM 생성은 planner가 Knowledge 필요성을 명시하지 않았더라도 `after_graph` / `binding_only` Knowledge 선택 단계를 만든다. 기존 `configure_and_generate` 입력은 같은 mode로 정규화한다. 이는 planner JSON을 재해석하는 규칙이 아니라 LLM node의 선택 가능한 binding을 확인시키는 Catalog 정책이다.
- 사용자는 하나 이상의 권한 있는 Knowledge Base를 고르거나 명시적으로 Knowledge Base 없이 계속할 수 있다. 선택 뒤 planner나 자연어 요청을 다시 실행하지 않는다.
- Knowledge candidate의 인덱싱 준비 상태는 생성 또는 binding 선택을 막지 않는다. 사용 권한과 source lifecycle만 후보 노출 경계이며, 준비되지 않은 binding은 실제 실행과 배포 preflight에서 차단한다.
- Knowledge/Parameter 카드가 열려 있어도 새 자연어 요청 composer는 잠그지 않는다. 네트워크 요청 또는 graph 저장 중인 경우만 제출 control을 잠근다.

## 2026-07-15 Correction: External Connection Guidance And Canonical Hydration

- Decision item 21의 Slack/GitHub `credential_ref` task와 빈 picker/defer presentation은 폐기한다. Mail/Gmail은 node runtime이 관리 credential reference를 요구하므로 기존 organization-scoped, use-permitted reference picker를 유지한다.
- Slack/GitHub는 Agent Builder가 node 구조를 생성할 수 있으나 credential 후보를 조회하거나 token을 입력·저장하지 않는다. 해당 node는 `configuration_state=unresolved`로 남고, 동일 workflow 설정 결과의 외부 연결 안내에서 node별 `연결 설정으로 이동` action을 제공한다. action은 해당 node를 선택·focus하고 기존 Editor의 연결/인증 control을 연다. Agent Builder는 credential API, GraphMutation, workflow save, planner 또는 외부 action을 호출하지 않는다.
- unresolved Slack/GitHub는 저장 가능하지만 configuration preflight가 test, run, deployment를 차단한다. 기존 Editor의 수동 연결 설정이 완료된 뒤에만 server-derived state가 resolved가 된다. 조직 credential lifecycle, use permission resolver, safe reference binding 및 runtime preflight가 구현되면 Agent Builder credential 지원 여부를 별도 ADR로 재검토한다.
- 조직 credential resolver가 없는 기존 Slack/GitHub 연결은 Agent Builder managed `credential_ref`가 아니다. CAS는 final graph의 모든 resource-bearing field를 inventory하되, persisted base graph와 canonical 값이 같고 connection-relevant node data가 변경되지 않은 기존 Editor 연결만 `legacy_editor_connection`으로 분류해 불변 carry-forward할 수 있다. Agent Builder는 이 값을 추가·교체·삭제하거나 새 node에 복제할 수 없고, 신규·변경 reference 또는 등록되지 않은 resource-bearing field는 fail-closed한다. Carry-forward는 credential 사용 승인이 아니며 기존 Editor 저장 검증과 runtime/test/run/deployment preflight가 실제 외부 호출 전에 계속 권한·연결 유효성을 검사한다.
- Routing 안내의 `Routing 설정으로 이동`도 focus만으로 끝나지 않고 대상 LLM node의 Routing control을 연다. 이 navigation action은 routing rule을 만들거나 graph를 저장하지 않는다.
- Canonical graph를 Undo, Redo, acknowledgement 또는 response-loss recovery로 다시 표시할 때 client는 server graph에 없는 editor-only `displayNumber`를 재생성한다. 이 값은 graph hash, CAS payload 또는 server graph에 저장하지 않는다.
- resource/reference task는 candidate id와 server-issued `reference_value`를 모두 사용해 canonical graph의 기존 값을 hydrate한다. 권한 상실 또는 삭제로 어느 후보와도 대응하지 않는 값만 안전한 unavailable state로 표시하고, task를 완료로 추측하지 않는다.
